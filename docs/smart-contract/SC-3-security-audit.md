## Trust boundaries and call path

| Lines | Review |
| --- | --- |
| [4–20](../../contracts/VextridePaymentRouter.sol#L4) | Trusted code pins canonical USDC and Arc Mainnet 5042. The amount cap keeps a six-decimal amount times 10¹² within uint256. It is a representation bound, independent of available funds. The only application storage is one map entry per successful payer/reference pair. The inherited guard uses a separate fixed slot. The recipient is immutable. |
| [22–46](../../contracts/VextridePaymentRouter.sol#L22) | Constructor rejects wrong chain, zero, the router itself and the canonical token as recipient. It requires token code and a successful metadata response consisting of one word equal to 6. Metadata confirms an interface property. The chain and fixed system address establish token identity in the approved environment. The operator must establish recipient control and eligibility separately. |
| [48–59](../../contracts/VextridePaymentRouter.sol#L48) | `pay` is nonpayable and guarded before the body runs. It validates chain, reference, amount, distinct payer and recipient, and the caller's unused reference. It tentatively reserves the reference before any token call. The caller is the only debit identity. Smart wallets and other intermediaries are the payer when they call the router. The API has no caller-selected recipient, arbitrary source or relayer authorization. |
| [60–64](../../contracts/VextridePaymentRouter.sol#L60) | Two external `balanceOf` calls are static. A reverting or undecodable read fails the payment. SafeERC20 calls the fixed token with caller-to-recipient `transferFrom`. Token reverts or false results fail. The wrapper can accept empty return data from a contract, so the independent exact-credit check also matters. The comparison avoids underflow and rejects balance decreases, zero movement, under-credit or over-credit given accurate balance reads. The guard blocks nested payment against both matching and different reference values. A revert unwinds the reservation, token writes and on-chain logs. A prior approval and execution gas are independent. |
| [66–75](../../contracts/VextridePaymentRouter.sol#L66) | The router emits one `PaymentSettled` after the assertion and has only read access to the used-reference flag. No owner, fee, pause, rescue, proxy, native entry point or recipient setter exists. The guard releases after completion. |

Public callers choose a reference and amount. A different caller can use the same bytes without consuming the intended payer's entry or using their allowance. A payer can consume its own reference with an incorrect amount. Same-payer concurrent calls with one reference race for the first successful settlement and a mined duplicate can cost gas. Work per payment is constant with respect to prior references. Repeated calls and storage growth cost the submitting payer gas. A canonically blocked payer, router or recipient or unavailable token path can prevent settlement. There is no router-level override. Chain or protocol changes can alter the behavior of the same system address.

A balance delta alone relies on the canonical token truthfully reporting balances and honoring its transfer semantics. The router does not inspect logs during execution. A future reconciler must verify the intended chain, reviewed router address and runtime, matching transaction and successful receipt, direct payer call and exact calldata with zero native value, the router's matching event, and the canonical six-decimal token event in that same receipt. Filter by emitters and count the payment once. The native system event, when present, represents the same movement in 18-decimal native units. Gas uses native USDC and remains separate from settlement. Undocumented or ambiguous event evidence should remain unresolved. A verified payment does not establish invoice authorization or fulfillment. ## Findings

| ID and severity | Prerequisite and impact | Verification, mitigation and remaining risk |
| --- | --- | --- |
| M-01 · Medium, confirmed design exposure | A sender transfers tokens directly to the router. The ERC-20 path can credit it with no settlement and no router recovery method. Native value can also be credited without the ordinary call path where the protocol allows it. [Payment entry and full public surface](../../contracts/VextridePaymentRouter.sol#L51) | The standard direct-transfer test shows the credit remains after normal settlement and produces no router event. The native-value test rejects payable calls and the privilege test models an unsolicited native balance locally. Protocol-specific forced-transfer restrictions were reviewed in Arc documentation. A genuine forced credit was not exercised in the Arc fork. Future instructions must distinguish router payment from a direct send. The owner must accept possible permanent loss. [Standard suites](../../contracts/test/VextridePaymentRouter.t.sol) · [Arc value transfer rules](https://docs.arc.io/integrate/evm-differences) |
| M-02 · Medium, operational prerequisite | An operator selects a valid-format but incorrect, inaccessible or ineligible immutable recipient, or loses control later. Valid payments could credit the wrong party permanently, or the router could become unusable. [Constructor](../../contracts/VextridePaymentRouter.sol#L35) | Constructor tests reject zero, token and self. The fork confirms the supplied synthetic recipient is bound and paid. The ABI and sequence checks show no setter. Verify the real recipient's checksum, control and Arc receipt eligibility independently before any later deployment. A replacement leaves the old address callable and cannot undo a settled payment. No specific production recipient was reviewed. |
| L-01 · Low, confirmed scope limitation | A future reconciler keys on the raw reference alone. Two legitimate payments can share its bytes across payers or deployments, causing incorrect attribution or duplicate fulfillment. [Reference state and settlement event](../../contracts/VextridePaymentRouter.sol#L20) | The SC-2 deployment-isolation test and Arc two-payer test demonstrate the distinct domains. Scope a settlement by `(chain ID, router address, payer, reference)` and verify expected recipient and amount. Use a separate off-chain order idempotency key across deployments. Forks inheriting the same chain ID and state are outside the guarantee. |
| L-02 · Low, confirmed protocol behavior | A payer grants approval and subsequently abandons the payment or the payment reverts. The earlier allowance can remain. [Token interaction](../../contracts/VextridePaymentRouter.sol#L60) | Standard tests observe allowance rollback after payment faults. The Arc suite observes successful finite allowance consumption, no allowance on the failed first attempt and no additional consumption on duplicate reference. Future UX should present the spender, suggest exact finite approval when required and explain remaining allowance. The router can only initiate payment for its caller to the immutable recipient. |
| I-01 · Informational, fixed | The two pasted fork tests used the Solidity-reserved identifier `reference`, blocking test compilation. The issue was in the test source. [Arc fork tests](../../contracts/test/VextrideArcFork.t.sol) | Renamed the affected locals to `paymentRef`, formatted and verified compilation and all four original fork tests before adding cases. The production source and ABI are unchanged. |
| I-02 · Informational, environment limitation | Running the standard `vm.etch` mock suite under Arc execution mode uses generic ERC-20 storage assumptions at a protocol-managed address. The owner observed 21 passes and 16 failures, including enum and blocked-address setup errors. | Treat those results as fixture incompatibility. This review used Ethereum-mode Forge for synthetic token faults and Arc Foundry in Arc mode for genuine USDC code. The 21/16 owner run was not counted as security evidence or rerun. A canonical token upgrade or future Arc release still requires a fresh compatibility check. |

No production router fix was warranted by the reproduced findings. Added mock regression cases for the maximum representable amount, excess credit, and a failed second balance read after the mock transfer. The latter two check rollback of balances, allowance and reference and the absence of a router event. The second-read test also verifies a subsequent valid retry.
