## Integration

- [Contract and ABI](../../src/game/blockchain/routerContract.ts) pin the deployed Arc Mainnet address, immutable recipient and deployed runtime Keccak-256. Before quoting either action, the RPC reader checks chain 5042, deployed runtime bytes and both `recipient()` and `usdc()`. The same checks run again before wallet handoff and receipt verification.
- [Preflight and receipt verification](../../src/game/blockchain/routerRpc.ts) check the reference, allowance, exact positive six-decimal amount and native funds for the fees. A short allowance produces an ERC-20 `approve(router, amount)` review. It simulates the approval and shows its fee cap plus a provisional gas reserve for the later payment. After approval, VEXTRIDE rechecks the allowance, simulates `pay(reference, amount)` and asks for an independent payment confirmation. It requests zero native transaction value and sets an explicit gas limit and fee cap. Increased fees or a changed transaction step invalidate the previous confirmation. ERC-20 balance and 18-decimal native balance are two views of the same USDC. The app checks both constraints without summing them.
- [Session](../../src/game/blockchain/routerSession.ts) and [journal](../../src/game/blockchain/routerJournal.ts) reserve the intent before any provider dispatch. The versioned key is scoped to Arc Mainnet and payer, separate from direct-transfer history and game saves. It stores the latest intent per payer in that browser origin. CSPRNG-generated nonzero references stay constant between approval and payment. Web Locks, read-back validation and compare-and-save guard against parallel tabs. Wallet/account changes invalidate drafts. A late hash remains associated with the original payer.
- [Wallet UI](../../src/game/blockchain/RouterPayment.tsx) offers a separate fixed-recipient mode. The deployer/recipient cannot pay itself. The app asks for wallet access only on Connect and prompts for either transaction only after in-app confirmation. An approval receipt is checked for exact calldata, canonical `Approval` event and expected owner and spender. It never completes a payment or automatically sends the next transaction.
- Settlement requires the verified deployment, matching transaction and receipt, direct calldata and zero native value, matching payer, successful receipt, the exact router event and one matching canonical ERC-20 transfer log. The native companion log is ignored for accounting. A success status or hash by itself cannot establish settlement. A reloaded on-chain result is labeled as saved until checked again. The current verifier covers direct EVM calls from the connected payer. Batched or nested smart-account payments need a separate verification design. [Arc system events](https://docs.arc.io/arc/references/usdc-system-events) · [Arc fee rules](https://docs.arc.io/arc/references/gas-and-fees)

A timeout, unknown wallet result, missing receipt or mismatched replacement never causes an automatic resend. A matching replacement hash can recover an intent on positive mined evidence anchored after the reservation block. Only the original known hash may resolve to reverted. If a wallet cancellation or replacement cannot be tied conclusively to the saved intent, the journal remains locked. Recovery is by read-only recheck after reconnect, with a hash from wallet activity if needed. A storage failure before dispatch blocks the operation. If saving a returned hash fails, the app can still show that hash in memory and retain the unresolved state on disk.

## Release audit and limits

The production dependency-tree audit reported 37 advisory entries across eight packages, 16 high, 15 moderate and six low. No rendered Rollup module came from the affected packages `@grpc/grpc-js`, `decode-uri-component`, `elliptic`, `stream-json`, `toml`, `undici`, `uuid` or `zod`. This reduces browser exposure for the inspected build. It is not evidence that the installation or operator tooling is free of exposure. There are no new app dependencies. Use frozen installs, a clean build environment and the static Pages artifact only. Review updates to the legacy tooling separately. [Prior release dependency review](../phase74/security-review.md)

Pages requires no credentials or application environment variable. Vite disables dotenv loading and custom client environment injection. Development CORS uses Vite's default and the development host allowlist is scoped to Loopback defaults and Studio domains. The static CSP passed the Chromium check with the existing game shaders and optional wallet. The real Pages service, HTTPS wallet extension permissions and Safari/Firefox still need owner smoke tests on the chosen origin. SwiftShader results do not establish hardware performance.

The public Arc RPC is an availability and correctness dependency. Contract identity is pinned and mismatches fail closed. Router reads use the configured RPC only, with CCIP Read and HTTP redirects disabled. A compromised wallet, deployment origin or RPC can misrepresent user intent or evidence. Exact value approval can remain on-chain when payment is abandoned. Browser clearing can erase local recovery data, and different origins do not share the journal. Immutable recipient and stranded-funds limitations remain. No production publishing or real USDC submission was performed.

The [Cloudflare runbook](../cloudflare-pages-release.md) contains the free deployment configuration, owner-only acceptance procedure and rollback instructions. The UI and static build are ready for owner review. Real payment acceptance stays **PENDING** until an authorized payer other than the immutable recipient demonstrates independently verifiable settlement.
