# VEXTRIDE SC-1 — Contract architecture and security specification

**Decision proposed for owner review. Keep the accepted direct USDC flow. Advance a router to SC-2 only if the owner identifies a real need to reconcile payments to a designated recipient using on-chain references.** A future game purchase requires its own product and fulfillment design.

## 2. Options and recommendation

| Option | What it provides | Cost and decision |
| --- | --- | --- |
| A. Existing direct ERC-20 transfer | Payer selects a recipient. A matched transaction hash and USDC log evidence support transfer verification. | One transaction with no allowance. No contract-level application reference or order reconciliation. Recommended for the accepted game. |
| B. Fixed-recipient payment router | A payer calls a verified contract. It forwards USDC directly to its designated recipient, consumes a payer-scoped reference and emits a receipt event. | Normally two transactions when allowance is missing. Adds approval, contract, operations and reconciliation risks. Consider only for an approved fixed-recipient use case that needs references. |
| C. Purchase contract | Settlement could be tied to actual products, agreed prices and an independently defined fulfillment model. | Requires a product catalog, durable ownership or delivery rules, support and review. Defer until there is a defined service. |

A router is justified only when matching the existing direct transfer after settlement is insufficient for a real operational need. The proposed candidate below is conditional. Its public event is a payment record. It carries no Street Cash, pricing, item, refund or entitlement state.

## 3. Arc units and transaction choices

| Operation | Exact units and evidence | Consent and tradeoff |
| --- | --- | --- |
| Existing direct ERC-20 `transfer` | Six-decimal token amount. Verified using the ERC-20 emitter and approved direct calldata. | One wallet transaction and no allowance. |
| Proposed ERC-20 `transferFrom` | Six-decimal token amount. Router pulls directly from the authenticated caller to the immutable recipient. The transaction sends zero native value. | With sufficient allowance, one payment transaction. Without it, a separately reviewed approval for the verified router and a second payment transaction. Unused allowance can remain after a failed or abandoned payment. |
| Native-value forwarding, evaluated and excluded from the candidate | A payable call would receive `msg.value` in 18-decimal units. Receipt evidence would distinguish the caller-to-router and router-to-recipient legs. A native-only send does not supply the six-decimal ERC-20 event. | One payment transaction and no allowance. Adds an intermediate value balance during execution, recipient callback and native forwarding failure cases. Arc enforces value-transfer and blocklist rules that can cause reverts despite sufficient funds. |
| Gas | Native USDC in 18-decimal units. Fee cap is gas limit times max fee per gas. The receipt records actual execution fees. | Fund both steps when approval is needed. Gas is operational cost, separate from the payment amount. |

Use integer token units at contract boundaries. For example, `1.234567 USDC` is `1_234_567` token units or `1_234_567_000_000_000_000` native units. Multiply a six-decimal amount by `10^12` before comparing it with native balance or adding a fee. Use checked math and recheck affordability at each consent step. Treat ERC-20 and native balances as two views of the same funds. The ERC-20 view can omit native dust. A direct ERC-20 movement can emit both the six-decimal token log and the 18-decimal EIP-7708 system log. Reconcile one movement. Fees are derived from receipt fields and do not generate USDC payment logs. [Stablecoin native model](https://docs.arc.io/arc/concepts/stablecoin-native-model) · [USDC system events](https://docs.arc.io/arc/references/usdc-system-events) · [Gas and fees](https://docs.arc.io/arc/references/gas-and-fees) · [EVM differences](https://docs.arc.io/integrate/evm-differences)

An eventual client should display the chain, router address, recipient, reference, exact amount, spender and expected fees. Recommend finite allowance scoped to this router, ordinarily the exact intended amount. Use an existing sufficient allowance only after showing the actual spender and balance. Account for ERC-20 allowance replacement semantics when changing a preexisting nonzero allowance. Treat approval and payment as independent actions and never report settlement on approval alone. Permit, Permit2 and relayer signing are outside this proposal.

## 4. Conditional interface for SC-2

Proposed name is `VextridePaymentRouter`. The following is an ABI sketch for review.

| Interface | Proposed rule |
| --- | --- |
| `constructor(address paymentRecipient)` | Require Arc Mainnet chain ID 5042. Reject the zero address, the router's own address and the USDC interface as recipient. Bind the one approved recipient permanently. Check the canonical USDC interface has code and reports six decimals. |
| `recipient() → address` | Read the immutable payment destination. |
| `usdc() → address` | Read the fixed Arc Mainnet USDC interface. The token address is a protocol constant, not a caller or owner setting. |
| `pay(bytes32 paymentReference, uint256 amount)` | Nonpayable. Source funds from `msg.sender`. Require the expected chain, nonzero reference, positive six-decimal amount within the underlying native conversion bound, a payer distinct from the recipient, and an unused reference for this payer. |
| `isReferenceUsed(address payer, bytes32 paymentReference) → bool` | Read recorded usage in this router's namespace. Reconciliation queries finalized chain state. |
| `PaymentSettled(address indexed payer, address indexed recipient, bytes32 indexed paymentReference, uint256 amount)` | Emit exactly once after verified settlement. Amount is in six-decimal units. Chain, router address, and the token getter identify the asset and deployment. |

Proposed error names are `WrongChain(actual)`, `InvalidRecipient(recipient)`, `UnsupportedUSDC()`, `InvalidReference()`, `InvalidAmount(amount)`, `PayerIsRecipient()`, `ReferenceAlreadyUsed(payer, paymentReference)`, and `UnexpectedRecipientCredit(expected, observed)`. Nonpayable entry points reject unexpected native value. Token and guard failures may propagate their own revert data. A failed payment never produces a successful router event.

**Storage and flow.** The only application state written for settlement is a nested map from paying address to reference to used flag, plus the state of the proposed reentrancy guard. This uses one entry per successful payer/reference pair. The recipient is immutable. There is no enumerable history or application balance. In a future client, review the intent, confirm any required approval, then recheck allowance, account, chain and fees before submitting the separately reviewed payment. The guarded call checks the request, reserves its reference, reads the recipient's ERC-20 balance, and uses SafeERC20 to move the exact amount from the caller directly to the recipient. It then re-reads the recipient's balance and requires an exact increase before emitting the event. A revert rolls back the reservation, transfer and logs. The exact-credit check adds two token reads. It rejects a false success or unexpected credit under honest balance reporting, but it cannot make a malicious or broken token truthful. The trust boundary is the fixed Arc USDC implementation.

**Replay scope.** A reference is consumed once per paying address per router instance. Chain and deployment provide separate domains. The reconciliation key should record chain ID, verified router address, paying address and reference, and retain the matching transaction hash and log index as evidence. Use opaque high-entropy references and avoid customer details or secrets in public calldata. A different payer can use the same bytes without consuming the intended payer's reference. A payer can choose an incorrect amount or consume its own reference. Off-chain reconciliation must check the expected payer, recipient, amount, deployment and reference. Across redeployments, any logical order also needs its own off-chain idempotency key. The router does not authorize signed meta-transactions or promise replay protection across forks sharing the same chain ID and state.

## 5. Trust model and security controls

| Concern | Candidate response and remaining exposure |
| --- | --- |
| Recipient authorization and custody | The owner approves a destination and checks control and receipt eligibility out of band before considering deployment. The deployer can choose initial inputs and gains no ongoing authority. Direct payer-to-recipient movement means normal payment execution credits no router balance. Funds arriving unsolicited are a separate case. |
| Recipient change, pause and owner privileges | Prefer one immutable recipient, no privileged owner, no pause and no upgradeable proxy. Pause would add an operator who can censor payments while leaving past transfers irreversible. For a bad recipient, stop client routing and retire the address. A replacement needs separate review, registration, allowance and cross-version reconciliation. Existing callers can still interact with the retired router. |
| Reference collision, griefing and front-running | Caller identity determines the reference namespace. Another account cannot mark an intended payer's reference or debit its allowance through this router. Timing may still cause a same-payer retry to revert and spend gas. User-selected references never grant delivery or authority. Ignore unexpected payers and amounts in reconciliation. |
| Transfer errors and reentrancy | Canonical token only, SafeERC20, atomic reference reservation and a reentrancy guard. SafeERC20 handles false returns and reverts and tolerates certain no-return implementations. An exact recipient credit is still required. Transfer failures, blocklisting and unsupported fee behavior surface as failed settlement. [OpenZeppelin SafeERC20](https://docs.openzeppelin.com/contracts/5.x/api/token/erc20#SafeERC20) · [Arc value-transfer rules](https://docs.arc.io/integrate/evm-differences) |
| Unsupported tokens and unexpected funds | The payment entry point accepts neither alternate tokens nor native value, and the router exposes no arbitrary calls or withdrawal methods. Reject regular native sends through its public surface. Other contracts or protocol mechanisms can still credit the address, and external ERC-20 transfers do not require router consent. Such funds create no payment record and could be permanently stranded. Accept that tradeoff explicitly or revisit the design separately. |
| Wrong network or malicious frontend data | Enforce the chain in construction and payment, and bind asset and recipient in code. Pin a verified deployment and runtime identity in a future client or reconciler. Show the exact reviewed values and recheck them before consent. The contract cannot prevent phishing, a lookalike router, compromised wallets or RPC misreporting. |
| Event authenticity and settlement | Verify chain, pinned router deployment and runtime identity, matching transaction and receipt, successful status, and exactly one matching settlement event from that router. Corroborate payer, recipient and exact six-decimal amount with the canonical USDC log from the same receipt. Validate hashes, positions and emitter addresses. Index native companion logs only as corroboration if needed. Ignore unrelated events, approval events and receipt success alone. |
| Consent, failure and recovery | The initial reconciliation policy for direct calls checks `tx.from`, `tx.to`, exact `pay(reference, amount)` calldata and zero native value. Arbitrary nested smart-wallet execution requires a separately reviewed policy. The contract uses `msg.sender` as payer throughout. After rejection, revert, timeout or replacement, inspect the approved intent and canonical chain record before deciding whether another payment is appropriate. An unknown outcome requires verification before another payment. An already-used reference cannot be reset. |

Security invariants for SC-2 are that a successful payment credits the fixed recipient exactly, preserves the normal router balance, consumes one payer-bound reference, and emits one matching event. Failed payments leave the reference usable and the transfer rolled back. Rollback can still cost gas for a mined revert. Another payer cannot consume that namespace or spend from the original payer's allowance. The router exposes no mutable recipient, fee, withdrawal, escrow or refund capability.

The current game verifier requires direct `transfer` calldata and the token as transaction destination. An eventual router integration would require a separate verifier and explicit approval. This specification preserves the current submission and history behavior.

A transient guard needs separate compatibility validation and offers no necessary behavior for this design. ## 7. SC-2 implementation and test matrix

If approved, implement the smallest reviewed router in `contracts/` and isolated mocks and tests in `contracts/test/`. First pin the behavior and errors, then run local unit, fuzz and invariant suites. Review the diff, ABI, compiler outputs and privileged surface before considering any fork or mainnet work. Preserve the accepted game and existing scripts.

| Local test group | Expected coverage |
| --- | --- |
| Constructor and configuration | Correct chain and token metadata. Reject wrong chain, zero recipient, router or token as recipient, missing token code and wrong decimals. Test the runtime chain check after local chain changes. |
| Successful payment | Mock six-decimal token. Assert exact payer debit, allowance consumption, exact recipient credit, unchanged router balance and the correct indexed fields, amount and emitter. Test smallest valid payment and reject self-payment and unintended value. |
| Validation and replay | Zero, overflowing or unsupported amount, zero reference, same payer twice, and different payers using the same reference. Assert failed attempts leave reference state unchanged. Independent deployments use independent namespaces. |
| Insufficient funds and transfer failure | Insufficient balance, missing allowance, token revert, false return, no-return success with exact credit, apparent success with no transfer, and fee-on-transfer under-credit. Assert complete rollback and no successful settlement event on every failure. |
| Reentrancy and malicious mock | Token callback attempts a nested payment with the same or a different reference. Verify guard, unchanged unrelated state and atomic rollback on propagated failures. Document the limitation of a deliberately dishonest token's balance reports. |
| Event verification | Wrong emitter, payer, recipient, amount or reference, duplicate logs, missing receipt, revert and mismatched calldata. Verify that native companion plus ERC-20 logs count one movement, and native-only evidence does not fulfill the ERC-20 verifier. |
| Stray funds and privilege surface | Reject ordinary native value. Model separately credited native or token funds. Verify no settlement event, no arbitrary withdrawals or configuration changes, and normal payments leave unrelated balances untouched. |
| Fuzz and invariants | Vary payer, amount, reference, balance and allowance over sequences of valid and failed calls. Assert at most one settlement per payer/reference per deployment, persistence after successful settlement, exact credit and isolation of unrelated payers. |

**Optional fork tests after local review.** Pin a public Arc block and verify the token bytecode, decimals, allowance, transfer failure behavior, exact credit and observed event emitters. Any simulated state changes stay in a disposable local fork with synthetic accounts. Verify Arc's blocklist, native-value and fork-tool differences separately. If faithful simulation or safe synthetic funding is unavailable, record the limitation. A funded mainnet wallet is not a test dependency. Optional public receipt reads can corroborate event behavior without demonstrating a VEXTRIDE payment.

## 8. Owner decisions and limitations

1. What real payment purpose and reconciliation need justify moving beyond direct transfers?
2. Who controls the fixed destination, how will ownership and receipt eligibility be verified, and who handles incorrect or unsolicited payments? Supply approved public deployment parameters only when relevant.
3. Who issues references, binds them to payer and amount, and owns cross-deployment idempotency? Is a different-wallet retry handled as an exception?
4. Is the two-step approval experience acceptable? Approve the choice to support only the canonical ERC-20 path and to reject native value.
5. Is the immutable, no-admin model acceptable, including potentially unrecoverable stray funds and inability to halt direct calls to a retired router?
6. If future payments buy a service, what are its order, fulfillment, recovery and support rules? Review that design before associating payment evidence with game state.
7. Does the owner authorize a local SC-2 implementation and an optional disposable fork review? Deployment, source verification and live wallet operations require separate authorization.

The design relies on Arc protocol and USDC behavior, accurate receipt data, review of the deployed bytecode, and the future reconciler checking its expected intent. It has no deployed router, audited implementation, hosted reconciler, demonstrated fulfillment, or live payment proof. A successful previous public receipt without a matching ERC-20 event is not payment evidence. [Release evidence](../phase74/evidence/live-rpc.json)
